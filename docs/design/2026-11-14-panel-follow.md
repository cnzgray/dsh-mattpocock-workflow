# 面板跟随：新会话自动恢复 MattWorkflow 页签（#43 的客户端半设计）

> 面向对象：工单 [#43](https://github.com/cnzgray/dsh-mattpocock-workflow/issues/43) 的落点选择与客户端半设计。
> 日期：2026-11-14。
> 依据：[`docs/research/2026-11-14-dsh-sidebar-right-session-scoped-state.md`](../research/2026-11-14-dsh-sidebar-right-session-scoped-state.md)（宿主右栏的会话级状态与可用 API）。
> 术语：设计词用**模块 / 接口 / 实现 / 接缝 / 适配器 / 深度 / 杠杆 / 局部性**；领域词用 **MattWorkflow 面板、右栏、页签、会话、视图偏好、能力诊断**（`GLOSSARY.md`）。

---

## 1. 落点选择

**选：插件侧「面板跟随」**——当在屏会话换人时，把 MattWorkflow 页签带到新会话里；宿主的 `openTab` 落在停靠面时会顺带展开右栏，两个可见结果由一条上游官方路径一次做完。

| 落点                     | 结论     | 理由                                                                                        |
| ------------------------ | -------- | ------------------------------------------------------------------------------------------- |
| **插件自动重开（跟随）** | **选它** | 唯一能在当前宿主版本上闭环的路径；用 `openTab` 的官方语义一次拿到「页签回来 + 右栏展开」    |
| 只展开不切页签           | 不选     | 右栏展开却是空的，用户还得再点一次；而且宿主只有切换语义的 `toggleExpanded()`，要自己兜幂等 |
| 只做引导                 | 不选     | 用户仍要点一次，困扰没消除；只适合当宿主能力缺失时的降级                                    |
| 改宿主                   | 不选     | 上游把「各 Session 独立保存状态」写成既定设计、明确不做跨会话继承；押注上游节奏不可控       |

**规则一句话**：_来源会话里开着 MattWorkflow 页签时，目标会话里没有，就替用户把它打开。_

规则不引入新的持久化：事实（哪个会话开着面板）本来就由宿主按会话持久化在 `dsh.sidebar-right.v1.<sessionId>`，宿主公开的 `openTabs` 清单读得到；再造一份工作区记忆就是第二个事实源，两边不同步时会出现「记忆说该跟、右栏里用户其实已经关了」。

## 2. 问题空间与约束

### 2.1 宿主事实（决定设计的四条）

1. 右栏**每会话一份**，新会话以折叠空面开始；没有「会话切换时复位展开状态」的代码。来源：研究笔记第 2 节。
2. `ctx.sidebarRight.openTab(kind)` 落在停靠面时**顺带展开右栏**；`openTabs` 清单给出每个会话开着的页签（含 `sessionId` 与 `kind`）。
3. `ctx.sidebarRight.mounted` 是**在屏会话**，它在 React 渲染该次切换**之前**就变了，而会话面（seat）在**同一帧**才铸出来——同步调用 `openTab` 会撞上 `sidebarRight: no session surface is mounted`。
4. 公开面上只有切换语义的 `toggleExpanded()`，没有幂等的 `expand()`；`openTabs` 只在 controller 实例上，不在 `ISidebarRight` 接口里（探测时按可选处理）。

### 2.2 仓库约束

- `client` 层只依赖 `protocol`（dependency-cruiser 的 `client-only-protocol` 规则）；不得 import `core` / `adapters` / `host`。
- 不得 import 上游 DSH 包；宿主能力一律**本地自声明的结构化类型 + 探测**（沿用 `readSlots` / `readTabs` / `readSessions` 的写法）。
- 测试跑在 jsdom（vitest），与源码同目录，测试名描述行为、不写工单编号。
- 能力诊断项在 `src/protocol/env-check.ts` 的 `UI_CAPABILITY_IDS` 增 id，文案在 `src/client/env-check-text.ts` 的 `CAPABILITIES` 表（宿主侧与界面侧共用一张表）。

### 2.3 依赖类别

| 依赖                    | 类别                                            | 缺失时                                             |
| ----------------------- | ----------------------------------------------- | -------------------------------------------------- |
| 宿主 `ctx.sidebarRight` | 宿主能力（我们不拥有的第三方包）→ 端口 + 适配器 | 不跟随；能力诊断记 `missing`；面板其余功能不受影响 |
| 浏览器 `localStorage`   | 本机可替换依赖                                  | **本设计不用**（事实由宿主持久化）                 |
| 宿主 `ctx.sessions`     | 宿主能力                                        | **本设计不用**（规则只需要 `sidebarRight`）        |

两个适配器（生产 = DSH 上下文，测试 = 假服务）→ 接缝是真的。

## 3. 候选设计对比

四个方案由四个独立子代理按不同约束产出（最小接口 / 最大灵活性 / 最常见调用方 / 端口与适配器），加上本次收敛出的方案：

| 方案                                         | 接口表面                                                          | 深度                                                       | 局部性                                 | 接缝位置                  | 主要代价                                                       |
| -------------------------------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------- | -------------------------------------- | ------------------------- | -------------------------------------------------------------- |
| 最大灵活性（策略注册表 + 偏好 + 事件流）     | 5 个文件、5 个类型（策略、决策、动作、事件、偏好）、模块 5 个成员 | **浅**：调用者要学策略契约、三个联合类型、事件流、偏好端口 | 差：时序、诊断、持久化分散在 5 个文件  | 端口在「决策」层          | 决策联合会随策略变宽；事件流是为尚不存在的引导与设置界面预留的 |
| 最常见调用方（一行安装 + 工作区门槛 + 记忆） | 1 个入口函数 + 2 个记忆函数 + 3 个结构化端口                      | 中                                                         | 中                                     | 端口在「宿主面」          | 多一份工作区记忆（第二个事实源）；策略并集是预留               |
| 最小接口（1 个入口 + 展开兜底 + 偏好开关）   | 1 个入口函数 + 2 个端口                                           | 中上                                                       | 好：一个文件装下时序、幂等、记忆、降级 | 端口在「宿主面」          | 同样带一份偏好开关；「新会话」判定用会话清单增长，有滞后风险   |
| **本次收敛（1 个入口 + 跟随上一个会话）**    | **1 个入口函数 + 1 个能力记录器参数**                             | **高**：调用者只知道「装上」                               | **好**：一个文件装下全部行为           | 端口在「宿主面 + 作用域」 | 规则窄：只跟随来源会话开着的场景；旧会话若来源开着也会被跟随   |

**取舍说明**：灵活性方案把「将来可能要」的东西（策略注册表、偏好里的 `policyId`、事件流、设置界面的数据位）提前做进了接口。按接缝纪律，**一个适配器意味着假接缝**——现在只有一种落点、一个调用方，策略注册表与偏好数据位都是**假想接缝**，属于为不存在的第二个消费者预先付出接口税。等真的出现「用户要能关掉跟随」或「不同工作区不同行为」时，再把策略接缝开出来，那时它有两个适配器（默认策略 + 用户选择）。

## 4. 选定设计

### 4.1 外部接口（接缝）

新文件 `src/client/panel-follow.ts`：

```ts
/**
 * 面板跟随：会话换人时把 MattWorkflow 页签带到新会话，宿主会顺带展开右栏。
 *
 * 深模块：调用方只说「装上」。会话判定、页签归属、落座时序、宿主能力缺失时的降级
 * 都在实现里，调用方不需要知道宿主服务名与页签 kind。
 */

/** 插件作用域：按名取服务，并能等依赖就绪。 */
export interface PanelFollowScope {
  get(name: string): unknown
  inject(deps: readonly string[], callback: (scope: PanelFollowScope) => unknown): unknown
}

/** 装上面板跟随时要说的事情。 */
export interface PanelFollowOptions {
  /** 要跟随的页签类型；本插件传自己的 kind。 */
  readonly tabKind: string
  /** 能力诊断记录器；模块用它报告宿主右栏控制能力是否可用。 */
  readonly capabilities: ClientCapabilities
}

/**
 * 装上面板跟随。
 * @param scope - 客户端作用域；模块在里面等 'sidebarRight' 就绪。
 * @param options - 页签类型与能力记录器。
 * @returns 停止跟随时调用一次的函数；重复调用安全。
 */
export function startPanelFollow(scope: PanelFollowScope, options: PanelFollowOptions): () => void
```

调用方（`src/client/index.tsx`）在**页签类型注册之后**加三行：

```ts
scope.effect(
  () => startPanelFollow(scope, { tabKind: TAB_KIND, capabilities }),
  `${PLUGIN_NAME}: 面板跟随`,
)
```

调用方因此**不需要**知道：`sidebarRight` 这个服务名、`openTab` 的展开副作用、`mounted` 的通知时机、「新会话」怎么判、页签归属怎么查、能力缺失怎么降级。

### 4.2 规则（实现里的一句话）

> 来源会话里开着 MattWorkflow 页签、目标会话里没有、且目标会话此前没被本模块见过 → 替用户打开它。

### 4.3 不变量

| 编号 | 不变量                                                                                                                   |
| ---- | ------------------------------------------------------------------------------------------------------------------------ |
| I1   | 每个会话最多自动打开一次；重复到达同一会话不重复 `openTab`。                                                             |
| I2   | 只对「本模块没见过的新会话」动作；切换到见过的旧会话不动作。                                                             |
| I3   | 目标会话里已经有本页签时不动它：既不重复打开，也不展开/收起右栏，不抢焦点。                                              |
| I4   | 来源会话里没有本页签时不动作（不打扰从未用过的会话）。                                                                   |
| I5   | 只调用 `openTab`；从不调用 `close` / `hide` / `toggleExpanded` / `focus`；不读写宿主的 `dsh.sidebar-right.v1.*` 私有键。 |
| I6   | 宿主没有 `sidebarRight` 时不动作、不抛错，能力诊断记 `missing`，并留一条 `console.warn`。                                |
| I7   | 停止函数幂等；停止后不再有订阅与定时器。                                                                                 |

### 4.4 顺序约束

1. **页签类型注册先于第一次 `openTab`**：否则宿主会因「kind 未注册」抛错。入口里三个注册 effect 建好之后再装跟随。
2. **宿主服务晚绑定**：模块内部 `scope.inject(['sidebarRight'], …)`，服务到了才开始观察；到了之后**立刻按当前快照判一次**（覆盖「插件装载时已经有一个会话在屏」的情况）。
3. **打开动作延后一轮宏任务，并在发出前复核「目标会话仍在屏」**：宿主 `mounted` 早于渲染变化，会话面在同一帧才落座，同步调用会撞上 `no session surface is mounted`；延后 + 有限次重试把这件事关在实现里。
4. **模块不抛错给调用方**：宿主异常一律吞掉并 `console.warn`。

### 4.5 错误模式

| 情况                                                     | 模块行为                                                   | 可见性                         |
| -------------------------------------------------------- | ---------------------------------------------------------- | ------------------------------ |
| 宿主没有 `sidebarRight`                                  | 不跟随                                                     | 能力诊断 `missing` + 一条 warn |
| 宿主实例上没有 `openTabs`（不在 `ISidebarRight` 接口里） | 无法判断页签归属 → **不动作**（保守）                      | 一条 warn                      |
| `openTab` 抛（会话面未落座 / kind 未注册）               | 延后一轮重试，若干次后放弃；该会话标记为已处理，不无限重试 | 一条 warn                      |
| 会话在等待期间被切走                                     | 放弃这一轮，不追打别的会话                                 | 无                             |
| 停止函数被重复调用                                       | 第二次起是空操作                                           | 无                             |

### 4.6 接缝后面藏了什么

1. **结构化探测**：`readSidebarRight(value)` 按本地自声明类型检查 `mounted`（`getSnapshot` + `subscribe`）、`openTab`（函数）、`openTabs`（可选）。
2. **页签归属查询**：从 `openTabs` 快照里找 `sessionId` 与 `kind` 都匹配的行。
3. **「新会话」判定**：模块自己记见过的会话 id（首次观察只记基线，不动作）。
4. **落座时序**：延后一轮宏任务 + 有限次重试 + 发出前复核仍在屏。
5. **去重三道闸**：会话级已处理集合、页签存在性检查、来源会话检查。
6. **降级**：宿主能力缺失、清单缺失、打开失败分别怎么处理。
7. **能力诊断**：`sidebarRight` 的有无记进诊断表。

### 4.7 内部接缝与适配器

外部接缝只有一个：`startPanelFollow(scope, options)`。内部接缝（只给模块自己的测试用，不从接口漏出去）：

| 内部端口                                         | 生产适配器                                    | 测试适配器                                                         |
| ------------------------------------------------ | --------------------------------------------- | ------------------------------------------------------------------ |
| 宿主右栏面（`mounted` / `openTabs` / `openTab`） | `readSidebarRight(scope.get('sidebarRight'))` | 假服务：可推进的 `mounted` / `openTabs` 快照 + 记录 `openTab` 调用 |
| 作用域（`get` / `inject`）                       | DSH 客户端作用域                              | 假作用域：按名字给出假服务，`inject` 立刻回调                      |

**为什么不再开一个「策略」接缝**：现在只有一种落点、一个调用方；策略注册表与偏好数据位是假想接缝。等真出现第二个消费者（例如用户能自己关掉跟随）再开，那时它有两个适配器。

## 7. 测试面

在模块接口上写（jsdom，假作用域与假服务，不连真实远端）：

1. **来源会话开着面板时，新会话自动恢复**：会话从 A 切到 B，A 的页签清单里有本页签、B 没有 → 宿主收到**恰好一次** `openTab(tabKind)`。
2. **来源会话没有面板时不打扰**：A 的清单里没有本页签 → 不调用 `openTab`。
3. **目标会话已经有面板页签时不重复打开**：B 的清单里有本页签 → 不调用 `openTab`，也不碰展开状态。
4. **切回旧会话不动作**：B 再切回 A（A 此前已见过）→ 不调用 `openTab`。
5. **首次观察不动作**：模块装载时屏上已有会话 → 不调用 `openTab`。
6. **会话在等待期间被切走就放弃**：延后期间屏上换成别的会话 → 不调用 `openTab`。
7. **打开失败不冒泡**：`openTab` 抛 → 模块不抛给调用方，且不无限重试。
8. **宿主能力缺失降级**：没有 `sidebarRight` → 不抛；`capabilities.read()` 里 `'sidebarRight'` 为 `missing`。
9. **清单缺失时保守不动作**：宿主实例上没有 `openTabs` → 不调用 `openTab`。
10. **停止函数幂等**：停止后再切会话 → 不调用 `openTab`；重复停止不抛。

入口级（`src/client/index.test.tsx` 扩一个用例，装配真实入口 + 假宿主）：**新会话到来 → 宿主收到 `openTab(TAB_KIND)`**——守住最常见调用方的真实路径。

## 8. 取舍与风险

**杠杆高的地方**

- 三个用户可见结果（新会话带上页签、右栏随之展开、不重复打扰）由**一个入口函数**换来；调用方知识量约三行代码。
- 宿主只有切换语义的 `toggleExpanded()`，本设计**完全不用它**——展开是 `openTab` 的官方附带语义，不需要自己兜幂等。
- 事实来源唯一：页签归属读宿主自己的 `openTabs`，不复制一份持久化。

**杠杆薄的地方（明确承认）**

- 规则窄：只在「来源会话开着面板」时跟随。要做「每个会话都跟随」「按工作区记住」「用户能自己关掉」都得再开一个接缝。
- 诊断只到「能力有无」，不解释「为什么这次没恢复」（来源没开？目标已有？能力缺失？）。要解释需要再开一个观察量。
- `openTabs` 不在上游公开接口里，探测按可选处理；上游改形状时表现为「不跟随」而不是崩溃。

**风险**

1. **上游漂移**（API 自述 pre-stable）：集中在探测层；行为退化为「不跟随」，能力诊断仍显示可用——这是已知的解释力缺口。
2. **落座竞态**：延后一轮宏任务 + 有限重试是对「渲染前通知、渲染中铸面」的推断；重试太少会漏恢复，太多会在会话切走后仍尝试（已用「发出前复核仍在屏」挡住）。
3. **焦点副作用**：`openTab` 会聚焦新页签，可能打断用户正在输入的提示词。
4. **右栏占屏**：自动展开右栏挤占对话区宽度——这是工单要的效果，但是用户可感知的代价。
5. **跟随范围**：切到「本模块没见过」的旧会话时，若来源会话开着面板也会被跟随（比工单字面要求更宽）。这是有意的取舍：面板跟着人走，而不是只在新会话里出现。
