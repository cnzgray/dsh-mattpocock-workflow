# dsh-mattpocock-workflow

在 DSH 里运行 [mattpocock/skills](https://github.com/mattpocock/skills) 工作流的 MattWorkflow 任务面板插件。

右侧栏新增一个“MattWorkflow”页签，含四个视图：

- **列表**：读取当前工作区的工单与“可接 / 阻塞 / 已关闭”统计，支持按状态过滤与按「分配给我 / 我创建的」过滤
  （两者各自独立，可同时开启取并集，并与状态筛选交叉生效）、按状态/更新时间/创建时间/编号/标题排序，
  并把“新建需求”“+ bug”“to-spec 需求”和每张票技能徽标对应的提示词按用户选择填进当前会话或新会话。
  “+ 新建需求”注入插件自带的 `/mattwf-feature` 和一个“一句话需求”槽位，“+ bug”注入 `/mattwf-bug` 和
  现象 / 复现步骤 / 预期行为三个槽位；两个入池命令只把报告写成一张原始工单——缺陷打 `bug` + `needs-triage`，
  需求只打 `needs-triage`，分类留给 `/triage`；不复现、不翻代码、不拆票，建完后给出票的链接和一行下一步建议就停下。
  入池命令随插件在内存里注册，不写入用户的技能目录。
  插件还注册 `/mattwf-close`：改动合并后，用户带上票的引用显式调用时，agent 读这张票的要求、之后的改动与评论，
  判断能否关闭；能关就先把判断依据写成评论再关票（GitHub / GitLab / Gitea 走各自 CLI，本地 Markdown 把
  `Status:` 改成 `resolved`），不能关或判断不了就只报告差什么，不动票、不改状态标签。
  “+ to-spec 需求”注入 `/to-spec` 和一个“需求描述：”槽位，不先入池：需求已经清楚时由技能直接建一张带规格、
  带 `ready-for-agent` 的需求票，之后按需拆票、实现；建票与打标签都在技能正文里，面板不代为执行。
  点击工单行打开详情；列表行与详情头部的技能徽标共用同一套判定，点击才填入对应技能的提示词；不可开工的票显示原因徽标，不提供注入入口。
  详情头部有手动刷新按钮：重读这张票并同步列表快照，失败时保留旧内容、在头部下方说明原因，不把详情切成错误页。
  工单提示词只有技能手势和工单引用（如 `/implement #40`），取票、实现、验证与复审都写在技能正文里，面板不复述。
  顶部三个按钮与工单技能徽标都是分裂动作：主键填进当前会话，右侧小箭头用同一段提示词直接开一个新会话
  （沿用当前工作区，草稿策略是追加，不自动发送）。环境检查的会话动作仍然只填当前会话。
  宿主不提供新建会话能力时只禁用小箭头，并在悬停说明与能力诊断里给出原因。
  默认只看未关闭工单，并按“可接 → 阻塞 → 其他开放 → 已关闭”排序；筛选、人员开关、排序键、布局与方向按工作区记住，
  重新打开面板或切回该工作区时恢复。偏好只存在浏览器本地存储里，不随工作区删除而清理，最多保留 50 个工作区条目；
  存储不可用时静默退回默认视图；
  列表支持**平铺**与**父子**两种布局，默认平铺：父子布局用已加载且通过当前筛选的票建树，子票逐层缩进，
  父行可收起整棵子树并显示可见子票数；父票被筛掉、还没加载、在别的仓库或是 GitLab epic 时，子票升到顶层并显示父级引用徽标，
  不伪造父行。GitHub 用原生子工单，GitLab 用工作项层级（列表返回后按每批最多 100 张票用一次 GraphQL 补齐，失败时只禁用父子布局、列表照常），
  本地 Markdown 用 `Parent:` 行；Gitea 没有原生子工单，用子票正文首行的 `Part of #编号`。布局只改变组织方式：
  判定、统计、筛选、排序、技能徽标、提示词注入与详情都不变；布局按工作区记住，切换不发请求；

- **概览**：一屏给出项目身份（仓库、后端、实例主机、快照时间、样本量）、压力总览（规模 / 阻塞 / 时效三张档位卡）、
  关键数字（开放积压、可接容量、待 triage、陈旧票、近 30 天新开与关闭、净流入）、状态与分类构成条，以及最多 5 张
  最该先看的票。三个维度各自判档，总档位取最重的一维；每条结论都带触发它的具体事实。点击关注清单里的票会切到列表并定位。
  后端给不出的指标显示“不可用”并说明缺什么，不用 0 或更新时间近似；样本被截断时，关闭类指标标注“可能低估”，
  由关闭数派生的净流入标注“可能高估”；
- **流程帮助**：面板顶部的 tips 图标打开，按场景分页签，用竖向排版的 SVG 流程图讲清入池与 triage 状态机、需求链、
  需求已明确时的直达规格路径、缺陷链、`/grill-with-docs` 与 `/wayfinder` 的取舍，以及实现之后的评审、PR 与关票（`/mattwf-close`）。图不可点击，图例区分插件自带的 `mattwf-` 命令与 matt 技能，
  并标出 agent 停下等用户发下一条命令的节点；从列表或环境检查进入，返回时回到原来的视图与筛选；
- **环境检查**：打开时自动逐项检查主目录、后端选择、后端 CLI 是否安装并登录、仓库是否可达、工作区是否初始化、
  本地工单目录（仅本地 Markdown 后端，或后端未判定时）、面板用到的技能是否安装。每个失败项给出与原因对应的解决：工作区、技能与本地工单类给会话动作（只填提示词、不发送），
  CLI、登录与远端类给可复制的命令和文档链接，超时与探测失败给“重新检查”。前置项没通过时后续项标为“跳过”，
  并提供跳到根因项的入口。底部折叠的“能力诊断”列出插件用到的 DSH 宿主服务和界面扩展点（含新建会话能力）是否可用，缺失项写明影响与补法。
  插件自带的 `mattwf-` 命令不计入“需要用户安装的技能”。缺两项以上技能时，检查项列表上方另有“技能总装”卡片，
  一条提示词一次装齐全部缺失技能；技能默认装到用户主目录（`~/.agents/skills`，`~/.dsh/skills` 同样有效），所有工作区通用。

面板本身只读工单与环境，不修改工单、不安装、不登录、不改用户的工作区文件，也不会自动发送提示词；建票与关票由 agent 按插件命令用跟踪器自己的方式完成，解决区只提供命令与提示词，不代为执行。

## 安装

三种方式效果相同，选一种即可；都要求 DSH `>= 0.2.0-rc.2`。

1. **按包名从 npm 安装**：`dsh plugin --profile <profile> add @cnzgray/dsh-mattpocock-workflow`。
   这是唯一支持「插件」页检查更新与就地升级的通道；包由 CI 用可信发布（OIDC）发布，带 provenance。
2. **一条命令从 Git 安装**：`dsh plugin --profile <profile> add github:cnzgray/dsh-mattpocock-workflow`。
   仓库自带的 `prepare` 会从源码构建出宿主入口与客户端 bundle。
3. **从 Release 下载预构建 tarball**：在 GitHub Releases 里取
   `cnzgray-dsh-mattpocock-workflow-<版本>.tgz`，再执行
   `dsh plugin --profile <profile> add /绝对路径/<文件>.tgz`。tarball 里已含构建产物，安装不触发构建脚本，
   适合网络受限、或想固定版本离线留存的场景。

Desktop 的 profile 由应用自己管理，在「插件」页安装即可；安装确认框会写明来源（npm 版本、Git 提交还是
tarball 资产），以及这次安装会不会执行构建脚本。上面的命令用于 web / tui 等自建 profile。

### 装不上怎么办

从 Git 安装会执行仓库的 `prepare`，pnpm 10 起默认拦下依赖的构建脚本。DSH 的安装界面会给出
**「允许这些脚本并重试」**，点它即可；用 CLI 时把 pnpm 报错里建议的键**原样**加进 profile 的
`pnpm-workspace.yaml`（`allowBuilds` 下一行 `<键>: true`）。键就是这次安装的 spec，不同 pnpm 版本
可能带、也可能不带末尾的提交号，以 pnpm 打印的为准：

```yaml
allowBuilds:
  '@cnzgray/dsh-mattpocock-workflow@github:cnzgray/dsh-mattpocock-workflow#<提交>': true
```

Release tarball 安装不需要这一步；从 npm 安装同样不触发构建脚本。

### 卸载

`dsh plugin --profile <profile> remove @cnzgray/dsh-mattpocock-workflow`；Desktop 在「插件」页移除。
卸载会一并移除 profile 里的组合包层，但不会删除插件自己的快照缓存
（`$DSH_HOME/cache/dsh-mattpocock-workflow/`，见下文），需要时手动删除。

## 界面语言

面板文案跟随 DSH 的界面语言（设置 → 通用 → 语言），当前提供中文与英文两套；其余语言沿 DSH 的回退链显示英文。
切换语言后面板立即改写，不需要刷新页面或重开面板。插件不另设语言开关，DSH 的语言设置是唯一来源。

- 宿主提供 locale 服务时，插件在浏览器端注册自己的命名空间词典（`@cnzgray/dsh-mattpocock-workflow`），
  面板通过同一个翻译入口取词；locale 服务晚于面板就绪也能接上；
- 宿主没有 locale 服务（老版本 DSH）时，面板使用内置中文词典，行为与接入前一致；
  环境检查底部的「能力诊断」会把「界面语言服务」记为缺失；
- 面板自己的全部界面文案集中在 `src/client/messages.ts`：中文是键集来源，英文必须覆盖同一组键（漏译在编译期失败）；
- 注入到会话里的提示词同样跟随界面语言，但技能手势与技能名（`/implement` 等）、仓库名、工单引用、
  状态/分类标签字面值、命令、路径与链接保持原样；
- 插件在「设置 → 插件」里的标题与说明来自随包发布的 `locale/<语言>.json`（英文为基准），
  `package.json` 的 `description` 只作兜底。补一门语言时新增一份与 `en` 同目录的词典文件，
  并在 `src/client/messages.ts` 增加对应词典；只交中英两套时，其余语言自动显示英文。

面板会在自己的缓存目录里保存最近一次成功拉取的工单数据（本地快照库），用于首屏先出数据与远端不可用时仍能查看：

- 位置：`$DSH_HOME/cache/dsh-mattpocock-workflow/`，未设置 `DSH_HOME` 时是 `~/.dsh/cache/dsh-mattpocock-workflow/`；目录不可写时退回系统临时目录。
- 每个工作区一个文件，存后端返回的原始工单、每张票的分配人、当前登录用户与拉取时刻，不存判定结果；判定按当前规则重算。
  缓存格式升到 4 后，没有人员或父子字段的旧条目会整体作废并全量重拉，避免把缺边的树当成完整数据。
- 打开面板先读库（不发远端请求），随即发起一次刷新把库推向最新：有可用库且后端支持增量时只取变更过的票，否则全量重拉。增量结果要与后端的权威总数对账，对不上（远端删过票）就当次改走全量。
- 面板开着时，agent 用跟踪器命令行建票、改标签、改状态或关票，这一轮结束后面板会自己做一次增量刷新；
  拉回来与当前显示的一致就不改动界面，数据变了才更新；无论哪种，筛选、排序、正在看的票与输入框里的提示词草稿都不受影响。
- 界面会标出数据来自「实时」还是「本地缓存」，刷新失败时保留旧数据并说明失败原因，不会清屏。
- 缓存只在插件自己的目录里，不写工作区，也不写仓库。卸载插件后这个目录仍会留在磁盘上，可以在环境检查里「清除本地快照库」，或直接删掉该目录。

工单后端按 `origin` 远端自动选择：

- `github.com` → GitHub，通过 `gh` 读取；
- `gitlab.com` 或 `glab` 已登录的自建实例 → GitLab，通过 `glab` 读取，支持嵌套 group；
- `tea` 已登录的自建 Gitea 实例 → Gitea，通过 `tea` 读取；
- 其余情况（没有 git、没有远端、主机不匹配）→ 本地 Markdown，读取
  `.scratch/<feature>/issues/*.md`。

面板顶部会标出当前后端（GitHub / GitLab / Gitea / 本地）；Gitea 后端还显示实例主机，便于区分多个
自建实例。四种后端共用同一套判定、统计、过滤排序与提示词注入。GitHub 在同一次 GraphQL 查询里取回
当前登录用户与每张票的分配人；GitLab / Gitea 在列表之外并行查询一次 `/user`。身份查询失败不影响列表，
只是人员筛选行不出现。本地 Markdown 没有创建人与分配人，因此不显示人员筛选行。

父子关系来源随后端不同，并且只用于组织列表：

- GitHub：列表 GraphQL 一并取父票编号与所在仓库；同仓库存 `#编号`，跨仓库存完整 `仓库#编号`，不新增请求；
- GitLab：列表仍走 issue 接口（默认同时返回 issue 与 task），返回后按每批最多 100 个 iid 用一次
  `workItems` GraphQL 补齐父级；父级是 Issue / Task 时存 `#iid`，是 Epic 时存 `&iid` 作为列表外引用。
  层级查询失败只把本次快照标为无父子能力，列表照常；增量与库的父子能力不一致时退回全量重拉；
- Gitea：没有原生子工单，父子能力为约定：子票正文**第一个非空行**写 `Part of #编号`（`to-tickets` 发布的
  ticket 就是这样挂到来源 spec 下），在已有列表响应里解析，不新增请求。这一行不在首个非空行、带引用块 / 标题前缀
  或多余文字、跨仓库写法、自引用都按无父级处理；父票正文里的任务列表不解析；阻塞依赖不当父级；
- 本地 Markdown：在 `Status:` / `Blocked by:` 同一段前言里写 `Parent: NN`，只认同一 feature 下存在的另一张票；
  评论里的 `Parent:`、缺失、自引用与跨 feature 引用都按无父级处理。

GitLab 的原生阻塞关系：首屏只等列表，阻塞数先按描述回退，原生阻塞数在列表显示之后补齐。
列表响应带 `blocking_issues_count` 时直接判定支持；否则按实例主机只探测一次，支持时用一次批量
GraphQL 查询取回阻塞数。不支持（Community 版对 links 接口返回
`200` + 空数组）或探测失败时只用描述 `Blocked by:` 回退，不再逐票请求。探测结果按实例主机缓存，
刷新不会重复探测。

## 环境要求

- DSH `>= 0.2.0-rc.2`；
- GitHub：已安装并登录 GitHub CLI（`gh auth login`）；
- GitLab：已安装 GitLab CLI 并登录（`glab auth login`）；自建实例需要登录该实例。
  最低支持 `glab` 1.126（本插件验证的版本）；更早版本未验证，登录状态识别失败时会回退本地 Markdown；
- Gitea：已安装 `tea` 0.16 或更高版本并登录实例（`tea login add`）；自建实例需要登录该实例；
- 当前工作区是 git 仓库且有远端；或直接把工单放在 `.scratch/<feature>/issues/NN-<slug>.md`
  （见 [本地工单约定](docs/local-issues.md)）。
- 同一个工作区有多个远端时，以 `origin` 为准；同一个主机同时出现在 `glab` 与 `tea` 的登录列表里时按
  GitLab 处理。

缺 `gh` / `glab` / `tea` 或未登录时，列表会显示对应的操作提示，并提供“查看环境检查”入口；读取 `.scratch` 失败时只给出文件权限提示。
自建 GitLab 或 Gitea 未在对应 CLI 登录时，面板回退本地 Markdown，并在顶部标明“本地”；环境检查会点名缺的是安装还是登录，
给出 `gh auth login` / `glab auth login` / `tea login add` 这类可执行建议。
Gitea 后端选定之后，如果 `tea` 不见了、令牌失效或权限不够，列表会显示安装或重新登录的提示
（`tea-missing` / `tea-unauthenticated`），环境检查里的 Gitea 三项也会给出同样的结论。
